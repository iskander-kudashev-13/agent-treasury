# Security audit — 2026-11-01

Pre-testnet audit of the Agent Treasury vault and its trust boundaries. Auditor: `security-auditor` agent
(`near-contract-audit` skill, all detectors in `references/{high,medium,low}-severity.md` walked).

## Scope

| Area | Files |
|---|---|
| Vault contract | `contract/src/{lib,payment,owner,agent,views,frequency,events}.rs`, `Cargo.toml`, `build.sh` (`tests.rs` read for coverage only) |
| Attestation dependency | `shade-attestation 0.2.0` (`attestation.rs`, `app_compose.rs`): what `verify()` actually checks |
| Worker | `worker/src/**` (payout loop, 1Click client, quote check, registration in `near.ts`, HTTP API), `src/ai/**` (assistant, NEP-413 session in `session.ts`, proposals, tools), `Dockerfile`, `docker-compose.yaml`, `deployment.yaml` |
| SDK / MCP | `sdk/src/**`, `sdk/scripts/*key-agent*.ts`, `mcp/src/**` |
| Dashboard | Only where it touches trust: wallet login, approval button, link building, build-time env |
| Secrets / supply chain | Working tree compared with `.gitignore`, all `.env*`, key-like strings in untracked files, lockfiles, version pins, Docker image contents |

Canon read: `CLAUDE.md`, `AGENT_ACCESS.md`, `UI_UPDATES.md` §3/§6, ADR-0001…0004 including the review amendments.

**Not checked:** nothing was deployed, signed or called on any network (as required). `cargo test` was not re-run (the
caller reports 151 green tests). Not checked: dstack / Phala KMS internals, the dcap-qvl verifier, 1Click's server-side
behaviour (refund semantics after deadline, quote signature format), NEAR AI Cloud attestation, dashboard pages beyond
the trust-relevant spots listed above, and transitive npm/cargo dependencies beyond "pinned + lockfile present"
(no `cargo audit` / `pnpm audit` run, because both need network access).

Overall: the contract's money path is solid. Reserve-before-transfer, a callback that never panics, atomic
`storage_deposit + ft_transfer` batches, re-checks at approval, schedule snapshots that are restored on failure, and the
inflow/outflow guards all hold up, including when agents, mandates, schedules, approvals and refunds interact. The real
weaknesses sit at the edges. The TEE measurement does not cover the config that decides where money goes. Owner
approval checks the destination the agent *declares*, not the one the deposit address actually pays. A few owner
methods that need no deposit are more powerful than their "restricting" label says.

## 🟠 High

### H1. TEE attestation does not pin the money-relevant configuration. The developer, or any tenant running the approved image, can redirect scheduled payouts.

**Where:** `worker/docker-compose.yaml` (`ONECLICK_BASE_URL: ${ONECLICK_BASE_URL}`, `ONECLICK_MODE`, `NEAR_NETWORK`,
`VAULT_CONTRACT_ID`, `AGENT_ID`, `DRY_RUN` are all `${…}` placeholders). `worker/src/config.ts`
(`ONECLICK_BASE_URL: z.url()`, any URL). `worker/src/quote-check.ts` checks the server's echo of `quoteRequest` but not
`signature`. `contract/src/agent.rs` `register_agent` / `tee_invalid_reasons`: approved measurements and PPIDs apply to
the whole vault, not to one slot. An unpinned slot binds to the first valid caller, and takeover is allowed once the
bound account's attestation expires.

**Attack:**
1. The dstack measurement covers the compose file *text*, so it includes `${ONECLICK_BASE_URL}` but not the value.
   Env values arrive encrypted and are not measured. `shade-attestation` explicitly accepts "any app compose
   configuration as long as the hash matches" (`attestation.rs` `verify_app_compose`: the config validation is commented out).
2. Whoever deploys the approved image picks `ONECLICK_BASE_URL=https://evil.example`. That is the developer, or any
   Phala tenant on a platform whose PPID the owner approved: the image digest and compose are public in this repo, so the
   measurements are reproducible. The fake server returns a quote whose `quoteRequest` echoes exactly what the worker
   expects, plus a `depositAddress` the attacker controls. `checkRealQuote` passes, because it trusts the echo.
3. Getting the agent role:
   - The developer is the operator.
   - A third party can call `register_agent` on any unbound TEE slot (window between `add_agent` and first boot, or after `unbind_agent`).
   - A third party can call it on any slot whose bound attestation has expired (worker down for more than about a day, or
     `attestation_expiration_time_ms` below the hard-coded 6-day refresh, see L5).
   - Measurements are vault-wide, so an image approved for `payroll` can also bind a different TEE slot, for example one with an `Open` mandate.

**Impact:** Every due Fixed/scheduled payment of that agent goes to the attacker's deposit address, up to the mandate's
`daily_limit` / `max_payments_per_day` and the vault `daily_limit`, until the owner notices. This breaks ADR-0002's claim
"In TEE mode … the developer cannot swap it for code that picks a different deposit address."

**Fix:**
- Make every money-relevant value part of the measured config. Write literal values in `docker-compose.yaml`
  (`ONECLICK_BASE_URL: https://1click.chaindefuser.com`, `NEAR_NETWORK: mainnet`, `ONECLICK_MODE: live`,
  `VAULT_CONTRACT_ID: <vault>`, `AGENT_ID: payroll`, `DRY_RUN: "false"`), or hard-code them in the image for `RUN_MODE=tee`
  and make `loadConfig` reject overrides in TEE mode.
- Keep only secrets (`ONECLICK_API_KEY`, `SPONSOR_*`, `WORKER_ADMIN_TOKEN`) in encrypted env.
- Verify the 1Click quote `signature` against a 1Click public key pinned in the image (ADR-0002 "Open for v2").
- Contract: add owner `pin_agent(agent_id)` (1 yocto) to pin the bound account after first boot, and scope approved
  measurements per slot (`Agent.allowed_measurements`), or at least document that approval is vault-wide.

**Reproduce (tester):** a worker unit test where `loadConfig({ RUN_MODE: "tee", ONECLICK_BASE_URL: "https://evil.example", … })`
must throw after the fix (today it succeeds). A payout-loop test with a fake 1Click that echoes the expected
`quoteRequest` and returns an arbitrary `depositAddress`: today `request_payout` is called with that address.

### H2. Owner approval shows the destination the agent declares, not where the deposit address really pays

**Where:** `contract/src/owner.rs` `approve_payout` (re-checks the declared `chain`/`address`, sends to the stored
`deposit_address`). `dashboard/src/components/Payouts.tsx:131` and `features/payouts` (Approve button, no 1Click lookup).

**Attack:** a compromised **key agent** (leaked function-call key, malicious MCP client, prompt-injected LLM) asks for
`request_payment(chain="base", address=<vendor in allowlist>, amount=<above threshold>, deposit_address=<quote whose recipient is the attacker>)`.
The vault cannot see the quote and parks the payment for approval. The dashboard shows "150 USDC → 0xVendor on base".
The owner approves, and the vault transfers to the attacker's deposit address. The same works for a TEE agent under H1.
The approval threshold is the main human control for large payments, and here it confirms the wrong thing.

**Impact:** up to `per_tx_limit` per approved payment, with a human signature behind it (worse audit trail: "the owner
approved it"). ADR-0003 §11 states that the destination checks prove only the declared destination. The UI does not warn about this.

**Fix (cheap, off-chain):** before enabling Approve, the dashboard calls `GET https://1click.chaindefuser.com/v0/status?depositAddress=<deposit_address>`
and compares the returned `quoteResponse.quoteRequest` with the payout:
- `recipient` must equal `payout.address`, and `destinationAsset` must be on `payout.chain`
- `refundTo` must be the vault, `refundType` must be `ORIGIN_CHAIN`, `amount` must equal `payout.amount`
- `deadline` must be in the future

Block the button on a mismatch or on an unknown deposit address. Show the verified recipient next to the declared one.
The worker's `reconcileSent` and the MCP status tool can apply the same check after the fact. Longer term: on-chain
quote-signature verification (ADR-0002 v2).

**Reproduce (tester):** dashboard unit test for an `approvalGuard(payout, statusResponse)` helper that returns blocked for
recipient, refundTo or amount mismatches.

## 🟡 Medium

### M1. Pending approvals survive an agent re-bind. The owner can approve a payout created by an account that no longer holds the slot.

**Where:** `contract/src/agent.rs` `unbind_agent` and `register_agent`'s takeover branch (`!current_valid`) do not touch
open approvals. `owner.rs` `approve_payout` evaluates the payout against the slot's *current* account and attestation
and never compares `p.agent_account` with `agent.account_id`.

**Attack:** account A (old enclave, or a dev key in local mode, believed compromised) creates PendingApproval payouts
with its own deposit addresses. The owner reacts with `unbind_agent` (or A's attestation expires and B takes over).
B registers validly. The old pending payouts now pass every check, because the agent is Active and its TEE registration
is valid. The owner approves one from the queue that is still tagged `payroll`.

**Impact:** up to 5 pending payouts × `per_tx_limit` chosen by the account the owner meant to cut off. Requires an owner
click, but the UI gives no hint that the requester changed.

**Fix:** in `unbind_agent`, and in `register_agent` when it binds a *different* account, call `reject_pending(id, false)`
for the slot's open approvals (the same loop as `revoke_agent`). Also require `p.agent_account == agent.account_id` in
`approve_payout` (or have `evaluate_payment` take the payout's account).

**Reproduce (tester, `tests.rs` harness, local mode):**
1. `add_agent("payroll", Tee, unpinned, Open mandate, approval_threshold=100)`; whitelist A and B; approve mock measurements and the default PPID.
2. A `register_agent`, then A `request_payment(amount=150, deposit=D_A, deposit_expires_at_ms=now+1d)` returns `PendingApproval{0}`.
3. Owner `unbind_agent("payroll")`, then B `register_agent("payroll")`.
4. Owner `approve_payout(0)`. Today it returns a transfer promise to `D_A`. Expected: panic, or the payout is already `Rejected`.

Variant: skip step 3's unbind, advance time past A's `valid_until_ms`, and let B take over.

### M2. Owner methods that need no deposit can be called with the dashboard's wallet login key. `unbind_agent` is not merely restricting.

**Where:** `dashboard/src/features/wallet/WalletProvider.tsx:62`, where `setupModal(selector, { contractId: VAULT_ID })` makes
MyNearWallet/Meteor add a function-call key for the vault with `methodNames: []` (any method) and store it in the
dashboard origin's `localStorage`. Owner methods that need no deposit: `pause`, `pause_agent`, `revoke_agent`,
`unbind_agent`, `reject_payout(skip)`, `pause_schedule`, `end_schedule`, `remove_recipient`, `remove_schedule`,
`remove_measurements`, `remove_ppids`, `remove_agent_from_whitelist_for_local`.

**Attack:** an XSS in the dashboard, or a malicious or compromised npm dependency in the bundle, reads the key and later:
- revokes every agent (terminal)
- ends every schedule (terminal)
- rejects pending salaries with `skip=true` (the date is gone for good)
- removes recipients
- calls `unbind_agent("payroll")`, which **opens** the slot to any instance of the approved image (chains into H1)

**Impact:** no direct theft, but permanent, hard-to-undo disruption of payroll. Combined with H1 it leads to fund
redirection. The kill switch staying FC-callable is intentional and fine.

**Fix:**
- Require 1 yocto for `unbind_agent` (it widens who can bind).
- Require 1 yocto for `reject_payout` when `skip == true`.
- Require 1 yocto for `revoke_agent` and `end_schedule` (terminal, irreversible).
- Keep only `pause`, `pause_agent`, `pause_schedule` deposit-free.
- In the dashboard, sign in without `contractId`, or restrict the login key to `methodNames: ["pause", "pause_agent", "pause_schedule"]`.

**Reproduce (tester):** existing tests that call these methods with zero deposit should flip to expecting the
"Requires attached deposit of exactly 1 yoctoNEAR" panic.

### M3. Insecure local mode can be enabled on mainnet without any explicit opt-in

**Where:**
- `contract/src/lib.rs` `new(requires_tee: bool, …)`: no guard, and the value is immutable after init.
- `worker/src/config.ts`: `RUN_MODE=local` is accepted with `NEAR_NETWORK=mainnet` (only `ONECLICK_MODE=simulated` is refused).
- `worker/src/near.ts`: in local mode the agent key is derived from `SPONSOR_PRIVATE_KEY` (`derivationPath`).

**Attack / impact:** a vault initialised with `requires_tee=false` on mainnet, which CLAUDE.md M2 plans for the demo,
trusts any owner-whitelisted account. Whoever holds the sponsor key holds the agent key. If a vault was set up for the
demo and later funded "for real", the TEE story silently does not apply. The dashboard shows only a small
"TEE required: false" text.

**Fix:**
- Contract: `require!(requires_tee || current_account_id ends with ".testnet" || allow_insecure_local_mode)`, with an
  explicit `allow_insecure_local_mode: Option<bool>` init argument that defaults to false.
- Worker: refuse `RUN_MODE=local` with `NEAR_NETWORK=mainnet` unless `ALLOW_INSECURE_LOCAL_MAINNET=true`.
- Dashboard: show a red "INSECURE LOCAL MODE" banner when `requires_tee == false`.
- README: state that the demo vault is local mode if it is.

**Reproduce (tester):** `new(requires_tee=false)` with `current_account_id = "vault.near"` must panic after the fix.

### M4. The "simulated 1Click" guard checks a network label, not the chain it talks to. Mainnet USDC can be sent to a random address.

**Where:**
- `worker/src/config.ts` superRefine, `sdk/src/client.ts:158`, `mcp/src/config.ts`: these refuse `simulated` only when the *label* `NEAR_NETWORK`/`TREASURY_NETWORK` ≠ `testnet`.
- `NEAR_RPC_URL` / `NEAR_RPC` / `rpcUrl` can point anywhere.
- `oneclick-simulated.ts` returns `randomBytes(32).toString("hex")` as `depositAddress`.

**Attack / impact:** a misconfiguration such as `TREASURY_NETWORK=testnet` with `NEAR_RPC=https://rpc.mainnet.near.org`
and a `.near` vault works, because NEAR transactions carry no chain id. The vault then really transfers USDC to an
implicit account nobody owns, and the funds are burned. Each such payment is bounded by the mandate, but losses are
permanent. Not reachable from the TEE compose (it does not pass `NEAR_RPC_URL`).

**Fix:** when `simulated`, call RPC `status` and require `chain_id == "testnet"`. Also reject vault and agent account
ids ending in `.near`, or 64-hex accounts, unless the network is mainnet. Apply the same check in worker, SDK and MCP.

## 🔵 Low / hardening

- **L1. `sync_surplus` / `credit_refund` can double-count an `ft_transfer_call` deposit that is in flight.**
  (`payment.rs` `on_sync_surplus`, `on_refund_balance`.) The `outflow_epoch` guard only covers outflows. If
  `ft_balance_of` runs after the token contract moved a deposit but before the vault's `ft_on_transfer` executes, the
  surplus is credited and then credited again by `ft_on_transfer`. Then `balance + in_flight > actual`. Anyone can
  trigger a deposit, so an attacker can front-run the owner's `sync_surplus` by donating tokens. Impact: phantom
  balance, later transfers or withdrawals fail and are released (no theft).
  *Fix:* accept `ft_on_transfer` only from `owner_id` (or an allowlist of funders), or add an `inflow_epoch` that is
  bumped in `ft_on_transfer`, read at call time and compared in the callback. Document "don't sync while a deposit is pending".
  *Reproduce:* call `sync_surplus`, then the `on_sync_surplus` callback with mocked `ft_balance_of = balance + D`, then
  `ft_on_transfer(D)`. Assert `balance + in_flight <= actual`.
- **L2. `new()` validates nothing.** `owner_id` may equal the vault or the token (after the vault's full-access key
  is deleted, a vault-owned vault is locked out). `policy` skips the `set_policy` bounds (`min_payment > 0`, grace in
  [1 h, 30 d]). `attestation_expiration_time_ms` is unbounded. *Fix:* reuse the `set_policy` checks and
  `require_bindable_account`-style checks in `new`.
- **L3. `force_settle_transfer` depends entirely on owner judgment.** A late callback is ignored once the payout is
  settled, so a wrong `sent` choice creates phantom balance (`sent=false` but the transfer went through) or loses a
  release. Document "verify on the explorer first". Consider allowing it only after the receipt is final (it always is
  after 1 h).
- **L4. Agents can flush the shared rejection log.** 50 entries per agent per day against a 200-slot ring. Two noisy
  agents erase everyone's history within a day. Events remain in the logs. *Fix:* per-agent rings, or a lower per-agent share.
- **L5. Worker re-registers on a fixed 6-day interval** (`near.ts` `SIX_DAYS_MS`), whatever the vault's
  `attestation_expiration_time_ms` is. A shorter expiry makes payroll stall, and the slot becomes takeable (H1).
  *Fix:* read `get_contract_info().attestation_expiration_time_ms` and refresh at half of it.
- **L6. `report_payout_status` lets the creating agent mislabel outcomes** (Confirmed vs Refunded/Failed). It moves no
  money and the balance guard holds, but the owner may miss a real refund or credit the wrong payout. `sync_surplus`
  recovers. *Fix:* the dashboard shows the 1Click status next to the reported one (same call as H2).
- **L7. When assistant signing lands in the dashboard** (not implemented yet, `AssistantPanel.tsx`), never sign a
  `call` from the worker as-is. Allow-list `method` against the proposal types in `proposals.ts`, force
  `receiverId = VAULT_ID`, and recompute `deposit`/`gas` client-side. A compromised worker host could otherwise propose
  `update_contract`, `withdraw` or `propose_owner`.
- **L8. In local mode the AI routes run in the same process as the agent signer.** A bug in `/ai` (SSRF, prototype
  pollution) shares memory with the key. The TEE compose does not pass `AI_SESSION_SECRET`, so `/ai` is off in TEE. Keep
  it that way, or run the assistant as a separate service.
- **L9. Sign-in challenge store is global** (`ChallengeStore` max 2000, 5-minute TTL). Distributed clients can exhaust
  it (per-IP limit 20/min) and block owner sign-in. *Fix:* per-IP cap, or stateless HMAC-signed challenges.
- **L10. Supply chain and image details.**
  - `contract/build.sh` builds without `--locked` (the reproducible-build metadata uses it). Add `--locked`.
  - The worker runtime image runs as root. Add `USER node`.
  - `deployment.yaml` has `public_logs: true`. Today's logs contain no secrets, so keep it that way and add a lint or test
    that config and keys never reach `console.*`.
  - `worker/package.json` pins `@types/node` with `^` (dev-only, harmless).
  - `mcp` depends on `agent-treasury-sdk` via `link:../sdk`. Fine in the repo, but pin a version before publishing.
- **L11. The design mock contains a key-like string.** `design-kit/…/canvas/AddAgent.dc.html:220` has an
  `ed25519:4fG8…` value of 73 characters. That is not a valid 64-byte key, so it is a placeholder, but secret scanners
  will flag it. Replace it with an obviously fake `ed25519:EXAMPLE…`.

**Contract, money path and cross-feature interactions**

- **Async failure.** `storage_deposit` and `ft_transfer` form one batch receipt, so they are atomic. Only
  `PromiseError::Failed` counts as failure, and `TooLong` counts as success (correct, since the receipt succeeded). On
  failure the callback releases balance, `in_flight`, and the agent and vault day counters (only if still the same
  day). It also restores the schedule snapshot (it undoes only an *automatic* `Ended`, and keeps an owner pause) and the
  recipient's `last_paid_at`. The storage deposit is refunded to the vault. A failed transfer can never be counted as
  `Sent`: `funds_left` is set only on success.
- **Agent abuse.** An agent cannot exceed per-tx, agent daily, vault daily, daily count, min payment, balance or expiry
  limits. It cannot pay while the vault or agent is paused or the agent is revoked or invalid. It cannot pay another
  agent's schedule, pay a schedule early, pay the wrong amount, approve its own payments, register another agent (Key
  kind cannot `register_agent`, and an account bound to another slot is refused), or forge a status that unlocks funds.
  Reports are annotation only, and `credit_refund` checks the real `ft_balance_of`.
- **Deposit address.** Must be a 64-hex implicit account and must not be the token, the vault, the owner, or any bound
  or revoked agent account.
- **Approvals.** `approve_payout` re-runs checks 1–11 for the payout's agent, enforces 72 h and the declared deadline,
  checks that the schedule still points to this payout for this exact `occurrence_at`, and does not double-count the
  daily count. Revoking an agent rejects its pending payouts. `update_schedule`, `update_recipient` and `end_schedule`
  cancel pending payouts and refuse while a transfer is in flight. `remove_recipient` and `remove_schedule` refuse while
  a payout is open.
- **Schedules.** A new schedule never owes past dates. Updates continue after the last handled or paid date (a late
  payment cannot pay twice). Rejected dates do not return unless the payout can no longer be approved. Overdue
  occurrences need approval.
- **Malicious caller.** `ft_on_transfer` accepts only the treasury token as predecessor, so a fake token contract is
  refused (its tokens are refunded). Callbacks cannot be invoked externally. Unknown callers of `request_payment` get
  `AGENT_NOT_FOUND` with no state written.
- **Owner lock-out.** `withdraw` ignores pause and agents and is limited only by available balance. `sync_surplus`,
  `withdraw_near` and `force_settle_transfer` give recovery paths. Ownership moves in two steps, the agent cannot become
  owner, and the owner cannot become an agent. Upgrades go through owner + 1 yocto + `migrate`.
- **TEE verification.** `verify()` checks: the Intel DCAP quote with collateral; `UpToDate` TCB; `report_data` equal to
  the caller's implicit account (padded); RTMR0-3, key-provider digest and app-compose hash against approved sets; PPID
  against the approved list; and the compose-hash event. Local mode requires the vault to be `requires_tee=false` at
  init and the caller to be whitelisted. Whitelisting is refused on TEE vaults. Mock measurements cannot pass real quote
  verification.

**Worker, SDK and MCP**

- The real quote is checked against the vault's recipient record: no dry quote, `EXACT_INPUT`, assets, recipient,
  `refundTo = vault`, `ORIGIN_CHAIN`, no `msg`, `amountIn`, implicit deposit address, deadline ≥ 5 min.
- Ambiguous `request_payout` errors are resolved by re-reading state and are never retried blindly. Polling is bounded.
  Reports are idempotent.
- `DRY_RUN` defaults to true. `simulated` is refused under the mainnet label (see M4 for the gap).
- `POST /run` uses a timing-safe bearer token and is disabled when unset. CORS is limited to `DASHBOARD_ORIGIN`.
- The NEP-413 session is correct:
  - digest: tag 2^31+413, borsh layout, `recipient = vault`, optional callbackUrl
  - single-use 32-byte nonce with 5-minute TTL
  - ed25519 check via the SPKI-wrapped key
  - the key must be a **full-access** key of `accountId` and `accountId` must be the vault owner (re-checked per chat, cached 60 s)
  - HMAC token bound to the vault, timing-safe comparison, 1 h TTL
- The assistant is read-only: no signer in `src/ai`, and proposals are limited to recipient, schedule, mandate and pause
  calls. Untrusted chain text is exposed only under `untrusted_*` with a system-prompt rule. Clients cannot inject
  system or tool roles. The privacy badge honestly reports "fetched_unverified".
- The key-agent script generates the key locally and prints it once. The function-call key is limited to
  `request_payment` and `report_payout_status` with a 0.25 NEAR allowance. Mainnet requires `--confirm-mainnet`.
  `OWNER_PRIVATE_KEY` is read from env only.
- MCP tool descriptions forbid splitting a payment and retrying after a rejection.

**Secrets and supply chain**

- The repo has one commit (`LICENSE` only), so there is no history to leak.
- No `.env` files exist. All five `.env.example` files have empty secret values. `.gitignore` covers `.env*`
  (except examples), `*.pem`, `*-key.json`, `.near-credentials/`, `target*`, `dist`, `node_modules`.
- The only key-like strings in untracked, non-ignored files are a test public key in `tests.rs` and the design
  placeholder in L11.
- The dashboard's `VITE_*` variables are public config only.
- The worker image:
  - base `node:22-alpine` is pinned by digest
  - pnpm 11.22.0 is pinned
  - `--frozen-lockfile`
  - prod dependencies only (the shade CLI and dev tools are not shipped)
  - only `dist`, `node_modules` and `package.json` are copied, and `.dockerignore` excludes `.env*`
  - `NODE_ENV=production` disables dotenv
- Every runtime dependency is pinned exactly (`save-exact`) with lockfiles present. Native build scripts are disabled.

## Trust boundary summary (for the README)

| Compromised party | Can | Cannot | On-chain cap that bounds it |
|---|---|---|---|
| **TEE agent (payroll), honest image** | Nothing beyond its code. Its key never leaves the enclave | Choose other amounts, recipients or dates | Mandate + schedules + vault policy |
| **Operator of the TEE image** (developer, or any tenant on an approved PPID when the slot is unbound or expired) — *until H1 is fixed* | Point the worker at a fake 1Click and redirect **due scheduled payments** to its deposit addresses. | **Key agent** (leaked function-call key, malicious LLM or MCP client) | Pay **any address it quotes**, whatever destination it declares (Open/Allowlist/Fixed alike), up to its limits. Exceed limits. Approve. Register agents | `per_tx_limit`, agent `daily_limit`, `max_payments_per_day`, `min_payment`, `expires_at`, vault `daily_limit`. Gas allowance 0.25 NEAR |
| **Worker host** (local mode) | Everything a key agent can, for the payroll slot (the agent key is derived from `SPONSOR_PRIVATE_KEY`). Read the NEAR AI key and session secret. Mint assistant sessions | Owner actions (the assistant cannot sign). Exceed limits | Same as key agent |

## Known limitations (documented trust assumptions for the README)

1. The vault cannot see 1Click quotes. For every agent kind it checks the destination the agent **declares**. Where the
   deposit address actually pays is trusted to the agent's code (TEE, once H1 is fixed) or bounded only by limits (key
   agents). Approving a payment approves the declared destination unless the dashboard verified the deposit address (H2).
2. The approval threshold can be split into several smaller payments. Only the daily amount and count limits bind.
3. Measurements and PPIDs are approved for the whole vault. Any instance of an approved image can bind an unbound or
   expired TEE slot. The owner should check the bound account after first boot.
4. Shade Agent v2 tooling is unmaintained upstream (ADR-0001). Versions are pinned, and the risk is ours.
   `shade-attestation` accepts any app-compose whose hash is approved.
5. Every payment costs the vault about 0.00125 NEAR (deposit-account registration) plus a payout record. The deposit
   account's owner (1Click, or an attacker under limitation 1) can reclaim that NEAR. Bounded by `max_payments_per_day`.
6. 1Click refunds arrive as plain transfers. The owner credits them (`credit_refund` / `sync_surplus`). Agent status
   reports are annotations.
7. 1Click has no testnet. The simulated mode fakes delivery and must never touch mainnet (M4).
8. Local mode (`requires_tee=false`) has no hardware guarantees. Whitelisted dev accounts act as the TEE agent (M3).
9. The NEAR AI attestation is fetched but not verified by the worker.
10. Owner full-access key compromise means total loss. Ownership transfer is two-step, but there is no timelock or multisig.
